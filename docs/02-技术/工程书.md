# 第一部分 · 系统概述

## 1.1 系统定位

**跳舞兰 H5 电商系统**是一套面向终端消费者的鲜花零售平台，由三部分构成：

| 组成 | 技术 | 作用 |
|---|---|---|
| 前台 H5 | Next.js 16（React 19 + TypeScript + Tailwind 4） | 面向消费者的购物界面 |
| 管理后台 | Next.js 16 | 面向运营人员的管理界面 |
| 后端服务 | FastAPI（Python 3.11） | 业务逻辑与数据接口 |

## 1.2 系统边界

本系统为**单一品牌自营**电商平台。以下事项由外部系统承担：

| 事项 | 承担方 | 本系统的职责 |
|---|---|---|
| 支付扣款 | 第三方支付网关 | 发起支付、接收回调 |
| 花艺制作与配送 | 合作履约方 | 推送订单、接收状态回传 |
| 商品基础数据 | 企业业务系统 | 通过接口同步 |

**设计原则**：本系统只负责「订单的创建、流转、追踪」，不承担物理履约。

## 1.3 系统目标

| 目标 | 技术实现 |
|---|---|
| 完整的线上销售闭环 | 订单状态机 + 支付回调 + 履约推送 |
| 运营可自助管理 | 独立管理后台 |
| 搜索引擎可见 | Next.js SSR/SSG + 结构化数据 + sitemap |
| AI 可调用 | MCP Server |
| 可持续扩展 | 三层架构 + 端口-适配器模式 |

## 2.3 为什么是三层架构

**问题**：如果路由里直接写 SQL + 业务逻辑，会发生什么？

```python
# ❌ 不推荐的写法：校验、算价、扣库存、写库、发通知，全在一个函数里
@router.post("/orders")
async def create_order(data):
    # 200 行代码，改一处要读完全部
```

**后果**：
- 改业务逻辑要懂 SQL
- 换数据库要改所有接口
- 没法单独测业务逻辑
- 多人协作时冲突不断

**三层架构**：

```python
# ✅ 路由层：只做转发
@router.post("/orders")
async def create_order(data: OrderCreate, service: OrderServiceDep):
    return ApiResponse(data=await service.create_order(data))

# ✅ 业务层：只管规则
class OrderService:
    async def create_order(self, data):
        # 校验库存、算价、扣库存、记日志
        ...

# ✅ 数据层：只管存取
class OrderRepository:
    async def create(self, obj):
        self.db.add(obj)
        await self.db.flush()
```

**好处**：
- 换框架只改路由层
- 换数据库只改数据层
- 业务逻辑可单独测试
- 各层职责清晰

## 4.1 订单状态机

```
                    ┌──────────────────┐
                    │  pending_payment │  待支付
                    └────────┬─────────┘
                             │
              支付成功 ──────┼────── 超时 / 取消
                             │                 │
                    ┌────────▼────────┐  ┌────▼──────────┐
                    │      paid       │  │  cancelled    │
                    └────────┬────────┘  └───────────────┘
                             │
                    推送履约方
                             │
                    ┌────────▼────────┐
                    │    preparing    │  配花中
                    └────────┬────────┘
                             │
                    履约方回传出发
                             │
                    ┌────────▼────────┐
                    │   delivering    │  配送中
                    └────────┬────────┘
                             │
                    履约方回传送达
                             │
                    ┌────────▼────────┐
                    │    delivered    │  已送达
                    └────────┬────────┘
                             │
                    用户确认收货
                             │
                    ┌────────▼────────┐
                    │    completed    │  已完成
                    └─────────────────┘
```

### 白名单校验

代码位置：`services/order_service.py::TRANSITIONS`

```python
TRANSITIONS = {
    "pending_payment": {"paid", "cancelled"},   # 待支付 → 已支付 / 已取消
    "paid": {"preparing", "cancelled"},         # 已支付 → 配花中 / 已取消
    "preparing": {"delivering", "cancelled"},   # 配花中 → 配送中 / 已取消
    "delivering": {"delivered"},                # 配送中 → 已送达
    "delivered": {"completed"},                 # 已送达 → 已完成
    "completed": set(),                         # 终态
    "cancelled": set(),                         # 终态
}
```

**作用**：防止状态乱跳。比如「已取消」不能变回「已支付」。

**实现**：所有状态变更都走 `OrderService.transition_status()`，先查白名单，不在白名单里直接抛 `InvalidStatusTransition`。

## 4.2 支付幂等

**问题**：支付网关的回调会重复发送（网络超时重试）。

**不处理会怎样**：
```
第一次回调 → 订单变「已支付」✅
第二次回调 → 又处理一遍 → 库存再扣一次 ❌
```

**解决方案**（`services/payment_service.py::handle_callback`）：

```python
# 1. 查订单时加行锁（FOR UPDATE）
order = await self.order_repo.get_by_order_no(order_no, for_update=True)

# 2. 幂等检查：已经不是「待支付」了，说明处理过，直接返回
if order.status != OrderStatus.PENDING_PAYMENT:
    return PaymentCallbackResult(
        order_no=order_no,
        status=order.status,
        idempotent=True,     # ← 标记这是重复回调
    )
```

**行锁的作用**：
- 两个回调同时到达
- 第一个拿到锁，处理完释放
- 第二个等锁释放后再查，发现已是「已支付」，直接返回

**验证结果**：重复回调返回 `idempotent: true`，订单状态不变。

## 4.3 库存扣减

**在建单时扣，不是支付时扣。**

**为什么**：防止超卖。两个人同时下单，只有一个能成功。

**代价**：用户不付款的话，库存锁 30 分钟（靠 `expire_at` 超时释放）。

**并发安全实现**（`repositories/product_repo.py::decrease_stock`）：

```python
# 用带条件的 UPDATE，数据库保证原子性
stmt = (
    update(Product)
    .where(Product.id == product_id)
    .where(Product.stock >= qty)      # ← 关键：库存够才扣
    .values(stock=Product.stock - qty)
)
result = await self.db.execute(stmt)
return result.rowcount > 0    # 返回 False 表示库存不够
```

**为什么不用「先查再改」**：
```
A 查询：库存 1
B 查询：库存 1
A 扣减：库存 0
B 扣减：库存 -1   ← 超卖了！
```

用 `WHERE stock >= qty` 是原子操作，只有一个能成功。

```python
class PaymentAdapter(ABC):
    @abstractmethod
    async def create_payment(self, order_no, amount, channel) -> dict:
        """发起支付"""
        ...

    @abstractmethod
    async def verify_callback(self, headers, body) -> bool:
        """验签"""
        ...

    @abstractmethod
    async def parse_callback(self, body) -> dict:
        """解析回调"""
        ...
```

**只改 `.env`，代码不动**：

```bash
# 开发环境

# 生产环境

```

### 新增渠道步骤

1. 新建 `adapters/payment/unionpay.py`，继承 `PaymentAdapter`
2. 在 `adapters/payment/__init__.py` 的 `_ADAPTERS` 字典加一行
3. `.env` 设 `PAYMENT_PROVIDER=unionpay`

**业务代码一行不改。**

## 4.5 配置管理

所有配置集中在 `core/config.py`，从 `.env` 读。

## 4.7 异常处理

**三层异常**：

| 类型 | 用途 | HTTP 码 | 示例 |
|---|---|---|---|
| `BusinessError` 及子类 | 业务错误 | 400/404/409 | 库存不足、订单不存在 |
| `RequestValidationError` | 参数错误 | 422 | 手机号格式不对 |
| `Exception` | 未预期错误 | 500 | 数据库连接断开 |

**统一返回格式**：
```json
{
  "code": "OUT_OF_STOCK",
  "message": "库存不足: 晨光序曲",
  "detail": {"product_name": "晨光序曲"}
}
```

**生产环境不暴露堆栈**：`settings_is_dev()` 为 False 时只返回通用错误信息。

# 第九部分 · 开发规范

## 9.1 注释规范

**每个文件开头必须有**：

```python
# ============================================================
# 【这个文件是干什么的】
# 一句话说清楚，不用术语。
#
# 【什么时候会用到】
# 什么操作会调用到这里。
#
# 【跟其他文件的关系】
# 谁调它，它调谁。
# ============================================================
```

**每个函数必须有**：

```python
def create_order(data):
    """
    【干什么】用户点「去支付」时，创建一笔待支付订单。

    【参数】
        data: 前端传来的订单信息，包含 items / receiver / ...

    【返回】
        成功：OrderCreateResult
        失败：抛异常（OutOfStockError / NotFoundError）

    【为什么这么写】
        - 库存在这里扣，不是支付时扣（防止超卖）
        - 运费满 199 免，不满收 15 元

    【注意】
        扣了库存如果用户不付款，库存锁 30 分钟。
    """
```

**关键代码行必须有「为什么」**：

```python
# 这里是防止重复支付：
# 支付网关的回调可能重复发多次，
# 如果订单已经是「已支付」，直接返回，不再处理。
if order.status != OrderStatus.PENDING_PAYMENT:
    return
```

**禁止的注释**：

```python
i += 1  # i 加 1         # ❌ 废话
i += 1  # 跳过表头那一行   # ✅ 说原因
```

## 9.3 金额规范

# 附录 · 常见问题

## Q: 为什么用 PostgreSQL 不用 MySQL？
A: PostgreSQL 的 JSONB、行锁、事务隔离级别更完善，适合电商场景。

## Q: 为什么用 Next.js 不用 Vue？
A: React 生态更大，Next.js 的 SSR/SSG 更成熟，招聘交接更容易。

## Q: 数据库迁移出错怎么办？
A: `alembic downgrade -1` 回滚一个版本，改完再 `upgrade head`。

## Q: 服务启动报「数据库连接失败」？
A: 检查 `.env` 里的 `POSTGRES_*` 配置，确认 PostgreSQL 服务在运行。

## Q: Windows 下中文日志乱码？
A: 设环境变量 `PYTHONUTF8=1`。

## Q: 怎么重置数据？
A: `alembic downgrade base` 然后 `alembic upgrade head` 然后 `python seed.py`。
