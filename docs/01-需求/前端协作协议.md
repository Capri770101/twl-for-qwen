# 跳舞兰 H5 · 前端协作协议

**文档编号**：TWL-COL-2026-001
**版本**：v1.0
**日期**：2026-10-20
**用途**：木木与 AI 协作开发前端时的**唯一沟通约定**。任何对话、任何 AI、任何设备，开工前先读这一份。

> 这份文件解决一个问题：**怎么说话，才能让 AI 交出来的是商用水准的前端，而不是一堆"看着还行"的页面。**

---

## 第一部分 · 谁管什么（先把权责切开）

前 10 轮沟通白费的根源，是两件事混在一起谈：**"做什么"和"怎么做"**。

| 事项 | 归谁 | 你怎么表达 | 我怎么给 |
|---|---|---|---|
| 业务规则、优先级、审美方向 | **木木** | 打勾 / 一句话 | — |
| 技术选型、代码结构、工程质量 | **小法师** | 不用管 | 出方案 + 说清代价 |
| 验收标准 | **共同**，但必须先写死 | 阈值或"能上线" | 逐条自检并给证据 |
| 项目状态（谁改了什么） | **文件** | 不靠对话记忆 | 落盘 + 版本号 |

**铁律：对话里的结论不算数，只有写进文件的才算数。**
多开对话时，这一条是第一生命线 —— 三个对话各改一版，谁都不知道对方动了什么。

## 第二部分 · 三段式输入（每次沟通只给我这三样）

### 2.1 模板

```
【目标】这次要达成的一件事（一句话，带验收标准）
【决策】A / B / C 选一个（我出选项，你打勾）
【禁区】不要动的东西（可选）
```

### 2.2 反例 vs 正例

| ❌ 会做废的说法 | ✅ 能落地的说法 |
|---|---|
| "做个好看的电商前端" | "移动端 H5，验收标准是：iPhone 12 上首屏 2 秒内出图，下单流程 3 步内完成" |
| "感觉差点意思" | "密度太松，商品卡一屏只出 2 个，我要 3 个" |
| "照着 XX 网站做" | "抄它的卡片留白和按钮圆角，配色还用我们自己的棕金" |
| "你先随便做，我看了再说" | "先出 1 屏让我看方向，方向对了再铺剩下的" |

**"你看着办"不是省事，是把返工风险转移给你自己。**

### 2.3 我出决策卡的标准格式

每轮我最多问你 **3 个决策**，每个给 2–3 个选项 + 一句代价。你只需要回 `1A 2B 3A`。

不给你开放式问题（"你想要什么风格？"）—— 那是把我的活推给你。

## 第三部分 · 我的交付格式（固定四件套）

每次交付必须带这四样，缺一样就是没做完：

1. **改了什么** —— 文件清单 + 一句话说明
2. **自检结论** —— 按第四部分验收表逐条打勾/打叉，**打叉的要说怎么补**
3. **怎么看** —— 可访问的 URL / 截图 / 命令
4. **下一张决策卡** —— 3 个选项，你打勾就能继续

> 我不说"已完成，你看看"。那不是交付，那是甩锅。

## 第四部分 · 商用水准 = 这张表（可测，不是形容词）

"商用"不是审美词，是一组**能被测出来的阈值**。下面每一条都是硬门槛，不是加分项。

### A. 设计系统（视觉一致性）

| # | 标准 | 阈值 |
|---|---|---|
| A1 | 颜色全部走 token，不出现裸色值 | 0 处 `#xxxxxx` 硬编码 |
| A2 | 字号阶梯固定档位 | 仅 12/13/15/17/20/24/30 六档 |
| A3 | 间距走 4px 栅格 | 0 处 7px、13px 这类野值 |
| A4 | 圆角/阴影/描边各 ≤ 3 种 | 超出就是失控 |
| A5 | 同一组件在不同页视觉一致 | 商品卡只允许 1 种实现 |
| A6 | 中文用组合字体，字重 ≤ 3 档 | 衬线标题 + 无衬线正文 |

> 现有 v10 原型的 token 已可用：`#FDFBF8` 米白底 / `#1A1512` 墨 / `#8B5E3C` 棕金主场 / `#F5EDE4` 浅棕。**设计不用重来，只需固化。**

### B. 性能（真机测，不是本机测）

| # | 标准 | 阈值 |
|---|---|---|
| B1 | LCP（4G + 中端安卓） | **≤ 2.5s** |
| B2 | CLS | **≤ 0.1** |
| B3 | INP | **≤ 200ms** |
| B4 | 首屏 JS（gzip） | **≤ 170 KB** |
| B5 | 首屏图片总量 | **≤ 300 KB**，hero ≤ 200 KB |
| B6 | 图片格式 | WebP/AVIF，一律带宽高（防抖） |
| B7 | 中文字体 | 子集化，首屏 ≤ 2 个字重 |

### C. 稳定性（商用和 demo 的分界线）

| # | 标准 | 具体要求 |
|---|---|---|
| C1 | 三态齐全 | 每个异步区块都有 **加载 / 空 / 错误** 三态，缺一即不合格 |
| C2 | 加载用骨架屏 | 不用转圈 spinner 硬等，骨架要与真实布局同形 |
| C3 | 空态可操作 | 空态必须给下一步动作（"去逛逛"/"重试"），不能只写"暂无数据" |
| C4 | 错误说人话 | "网络有点问题，点这里重试"，不暴露 `500` / `Internal Error` |
| C5 | 超时兜底 | 所有请求设超时（≤ 10s）+ 重试 1 次 |
| C6 | 支付幂等 | 重复点击只下一单；前端锁 + 后端幂等键双保险 |
| C7 | 支付超时 | 超时轮询订单状态，不直接判失败 |
| C8 | 断网可感知 | 断网时给提示条，不是静默失败 |
| C9 | 表单校验 | 失焦即校验，错误定位到具体字段，不弹 alert |
| C10 | 防重复提交 | 提交中按钮禁用 + 文案变化（"提交中…"） |

### D. 可用性与无障碍

| # | 标准 | 阈值 |
|---|---|---|
| D1 | 正文对比度 | ≥ 4.5:1 |
| D2 | 触控热区 | ≥ 44×44 px |
| D3 | 键盘可达 | Tab 能走完主流程，focus 可见 |
| D4 | 图片 alt | 内容图有 alt，装饰图 `alt=""` |
| D5 | 语义标签 | 导航/主区/页脚用语义标签，标题层级不跳档 |
| D6 | 字号不锁死 | 系统字体放大到 130% 不塌 |

### E. 商务与增长（老板真正在意的）

| # | 标准 | 落点 |
|---|---|---|
| E1 | 每页独立 title/description | 不共用站点标题 |
| E2 | OG / 分享卡 | 分享到微信有标题 + 图 + 描述 |
| E3 | Product JSON-LD | 商品页结构化数据（价格、库存、评分） |
| E4 | sitemap.xml + robots.txt | 自动生成，不手写 |
| E5 | GEO（AI 可见性） | 商品页有可抓取的规格/花材/配送说明 + FAQ 区块 |
| E6 | 埋点六件套 | `page_view` / `product_view` / `add_to_cart` / `begin_checkout` / `purchase` / `pay_fail` |
| E7 | 渠道参数 | 能识别 `utm_*` 与微信来源 |
| E8 | 微信环境 | iOS 安全区适配；微信内置浏览器实测一遍 |

### F. 工程（决定半年后还能不能改）

| # | 标准 | 阈值 |
|---|---|---|
| F1 | TypeScript strict | 开 `strict`，`any` 不得逃逸（最多 3 处且注明原因） |
| F2 | Lint / 类型检查 | 构建前必须全绿，0 error |
| F3 | 环境变量分环境 | dev / prod 分离，不写死域名 |
| F4 | 错误边界 | 单页崩不拖整站白屏 |
| F5 | 目录约定 | 组件 / 页面 / 请求 / 类型 四层分离 |
| F6 | 可回滚 | 每次可交付状态打 tag，出问题 1 分钟内回退 |

## 第五部分 · 每屏的"做完"定义（DoD）

一屏（一个页面）只有同时满足下面 7 条，才算交付：

- [ ] 接**真接口**（不是写死 mock；mock 阶段要明确标注）
- [ ] 三态齐全（C1）
- [ ] 375 / 390 / 414 / 430 四档实测不塌
- [ ] 埋点已埋并可验证
- [ ] 控制台 0 报错、0 警告
- [ ] 性能达标（B1–B4）
- [ ] 通过 F2（lint + 类型）

**不满足上面任何一条，我不说"做完了"，只说"到演示档"。**

## 第六部分 · 三档交付（先把档位说清楚，避免预期错位）

| 档位 | 长什么样 | 能干什么 | 谁看 |
|---|---|---|---|
| **原型档** | 单文件 HTML，假数据，静态 | 给老板看方向 | 老板 |
| **演示档** | 能点能走通，数据还是假的 | 内部演示、确认交互 | 老板 / 运营 |
| **商用档** | 真接口 + 异常处理 + 性能 + 埋点 + 无障碍 | 真客户能用、真收钱 | 客户 |

**说"商用水准"= 商用档，不是演示档。** 这两档之间的工作量差 3 倍以上，评估工期时必须区分。

## 第七部分 · 沟通反模式（这几句会让项目烂掉）

1. **"你看着办"** → 返工风险全转到你身上。至少要给一个参照物。
2. **多开对话各改一处** → 必然冲突。规则：**同一时刻只有一个对话能写代码**，其他对话只读或只讨论。
3. **只描述感受不指指标** → 说"不对"可以，但要指到"密度 / 配色 / 节奏 / 文案"中的一项。
4. **需求藏在第三人称里** → "老板说也许要…" 这种话我会当成 `[?]` 挂起，不实现。等确切了再说。
5. **跳过决策卡直接要成品** → 我会按自己的判断做，做完你不满意，双方都亏。
6. **拿旧对话的结论当现状** → 一切以文件和代码为准。

## 第八部分 · 当前状态（2026-10-20，需要一条决定）

**已核实的事实：**

| 项 | 现状 |
|---|---|
| 设计语言 | v10 原型已定型：米白底 + 墨色字 + 棕金主色 + 衬线中文标题，**可直接固化** |
| 原型资产 | `frontend/v1–v10`，共 10 版，v10 最完整（首页/列表/详情/下单/完成/订单/顾问 7 页） |
| 后端 | `app/backend`：FastAPI + SQLite，接口文档 `frontend/api-docs.md` |
| 前端工程 | `frontend/`：**Next.js 16.4.2 + React 19.3 + Tailwind 4 + TS**，脚手架建于 2026-10-20 14:26，`page.tsx` 仍是 create-next-app 默认页（未开工） |
| 工程书 v1.1 | 写的是「**纯静态 HTML + 原生 JS，不用 Vue/React，因为时间只有 3 天**」 |

**⚠️ 冲突：工程书和代码是两套现实。**

工程书按"3 天出 demo"的约束选了静态 HTML；`frontend/` 里已经把 Next.js 建起来了。这不是小事 —— 两条路线在**渲染方式、SEO 能力、后续扩展**上完全不同，两边并行写必然撕扯。

**决策卡 1（必须先答）：走哪条路**

| 选项 | 内容 | 好处 | 代价 |
|---|---|---|---|
| **1A** | Next.js（当前脚手架）做前台 + 后台 | SSR 天然满足 SEO/GEO 目标；组件化后 7 个页面复用度高；以后接千问、小程序可共用类型与请求层 | 要真学 Next 16 的新约定；构建链路比静态页面重；首屏 JS 需控制 |
| **1B** | 保留静态 HTML（工程书原方案），Next.js 只做后台 | 最快能看到东西，改一行刷新就生效 | SEO/GEO 靠手写静态页堆；7 个页面会有大量复制粘贴；半年后改不动 |
| **1C** | 静态 HTML 做对外 SEO 落地页 + Next.js 做交易流程 | 营销页极致轻量，交易流程工程化 | 两套技术要维护，一个人容易顾此失彼 |

> **我的判断：选 1A。** 理由：你的任务书第 1.3 节明确写了「搜索引擎可见性」和「AI 推荐可见性」两个目标 —— 那是静态 HTML 拼不太动、而 SSR 天生擅长的部分。工程书那句"3 天"是给 demo 的约束，不该管商用版本。但 1A 的前提是：**先把设计 token 固化了再写页面**，否则 React 会让"每页一个样式"的问题放大 10 倍。

## 第九部分 · 开工顺序（不要并行铺 10 个页面）

**错误顺序**：首页 → 列表 → 详情 → 购物车 → 下单 → 支付 → 订单 → 顾问 → 后台 → 打磨
（做到第 5 步发现 token 不对，前面全部返工）

**正确顺序**：垂直切片，一条链路打通再复制。

1. **固化地基**：design token（颜色/字号/间距/圆角）→ 基础组件（按钮/输入/卡片/弹层/骨架/空态/错误态）→ 布局壳（导航/页脚/安全区）
2. **打通一条链路**：商品详情 → 下单 → 支付 → 订单成功（真接口，含三态、幂等、埋点）
3. **复制扩面**：列表 → 首页 → 订单列表 → 售后 → 顾问
4. **商务加固**：SEO/OG/JSON-LD/sitemap、性能预算、微信环境实测
5. **后台**：运营用，标准可以低于前台，但权限与审计不能省

**每完成一步，我按第四部分自检并给证据，你只回「过」或「改哪」。**
